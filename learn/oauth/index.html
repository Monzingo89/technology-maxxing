OAuth 2.0

delegated authorization for api access

2026 · Daily Agent

Why learn OAuth 2.0?

OAuth 2.0 lets users grant limited app access to APIs without sharing their passwords. It standardizes scopes, token lifetimes, and delegated consent across clients, authorization servers, and resource servers.

Where it came from

2007-2010: OAuth 1.0 emerged to avoid password sharing but was hard to implement. 2012: OAuth 2.0 was standardized in RFC 6749 (framework) and RFC 6750 (bearer tokens). OpenID Connect (built on OAuth 2.0) became the common identity layer for login. Security guidance evolved through RFC 6819 and later OAuth 2.0 Security BCP. Current direction: OAuth 2.1 and FAPI profiles push safer defaults and remove weak patterns.

Catalog research notes

  • OAuth 2.1 draft consolidates best practices and removes risky legacy flows.
  • PKCE is now expected for public clients (SPAs and mobile apps).
  • Implicit grant and Resource Owner Password Credentials grant are broadly discouraged.
  • Sender-constrained tokens (mTLS, DPoP) are gaining adoption to reduce bearer-token replay.
