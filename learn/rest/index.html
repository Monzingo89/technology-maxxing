REST

architectural style for stateless web apis

2026 · Daily Agent

Why learn REST?

REST provides a consistent way to expose and consume resources over the web so clients and servers can evolve independently, scale horizontally, and use standard HTTP features like caching and status codes.

Where it came from

REST was defined by Roy Fielding in his 2000 dissertation as an architectural style, not a protocol. It emerged from lessons learned while designing the early web architecture. Core constraints include client-server, statelessness, cacheability, uniform interface, layered system, and optional code-on-demand. REST became the dominant public API style in the 2010s and remains foundational, though now considered mature/legacy in many stacks.

Build your understanding

Work through these exercises in order. Try the task before opening a reference.

  1. Given a Todo resource, choose GET/POST/PUT/PATCH/DELETE routes and matching success status codes (200, 201, 204). Keep routes noun-based.
  2. Design GET /products with pagination, filtering, ETag, and 304 handling. Include sample request/response headers.
  3. Convert endpoints like /createUser and /getUserById into resource-oriented routes. Add proper status codes for validation, not found, and conflicts.
  4. Propose a v1 to v2 migration plan using additive changes, deprecation headers, and compatibility tests.
  5. Define a reusable error response schema (code, message, details, traceId) and map it to 400/401/403/404/409/422/500.

Catalog research notes

  • HTTP semantics were consolidated in RFC 9110 (2022), clarifying method and status code behavior used by REST APIs.
  • HTTP/2 and HTTP/3 improved transport speed and multiplexing, while REST constraints remained unchanged.
  • Modern REST practice now commonly includes OpenAPI contracts, linting, and contract testing for consistency.
