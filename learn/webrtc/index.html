WebRTC

browser api for real-time media and data

2026 · Daily Agent

Why learn WebRTC?

WebRTC enables low-latency peer-to-peer audio, video, and arbitrary data exchange in browsers/apps without requiring plugins, while still supporting relay fallback when direct peer paths fail.

Where it came from

2010–2011: Technology from GIPS was open-sourced by Google and evolved into WebRTC. Standardization split: W3C defined browser APIs, while IETF defined transport/signaling-related protocols (ICE, STUN/TURN usage, RTP/DTLS/SRTP, SDP/JSEP flow). WebRTC replaced plugin-era real-time web communication approaches (for example Flash-based calling stacks). By the late 2010s, cross-browser support became practical; today it is a mature, foundational real-time web stack often treated as a 'legacy baseline' in product architecture.

Build your understanding

Work through these exercises in order. Try the task before opening a reference.

  1. Draw the exact signaling sequence for a browser-to-browser data chat: offer, answer, ICE candidate exchange, and connected state checks.
  2. Implement reconnect logic when network type changes (Wi-Fi to cellular). Log ICE state transitions and recovery time.
  3. Refactor a pure P2P group call design to SFU-based routing. Compare bandwidth, latency, and server cost trade-offs.
  4. Force TURN-only mode in a test room and measure quality impact vs normal ICE policy. Propose optimization steps.
  5. Audit your signaling and media path for identity, replay, and metadata leakage risks; provide mitigations.

Catalog research notes

  • Major browsers now align on Unified Plan SDP semantics; older Plan B behavior is effectively legacy.
  • Encoded media transform workflows (for advanced effects/E2EE patterns) continue to mature in Chromium-based environments.
  • Current ecosystem focus is interoperability, NAT traversal reliability, and lower battery/network cost on mobile.
